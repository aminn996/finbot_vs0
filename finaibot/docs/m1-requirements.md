## Critical requirement audit

### Risk thresholds and timing

The current implementation defines:

- Daily loss: `max(0, equity_at_day_start - current_equity)`, compared with initial capital.
- Total loss: `max(0, initial_capital - current_equity)`, compared with initial capital.
- Preventive events at `>= 4%` daily and `>= 8%` total; daily entry blocking lasts for the current calendar day and total preventive protection blocks new entries thereafter.
- Hard events at `> 5%` daily and `> 10%` total; `hard_breach` rejects the run, records the event, stops the simulation, and prevents end-of-data closure from converting the rejected run into a completed one.
- A value exactly at 5% or 10% is not treated as exceeding the cap, matching the specification's `<=` acceptance criterion. Boundary tests are in `tests/test_risk.py`.

The risk check runs at the following deterministic points: after a protective or rule exit, after completed-candle valuation of an existing position, after an accepted entry using entry-time estimated liquidation equity, and after the same bar's completed-candle valuation. A preventive event blocks later entries according to its scope. Risk events record timestamp, measured loss, equity, threshold, action, phase, and status (`PROTECTION_ACTIVE` or `REJECTED`); a hard event rejects the run. Invalid non-finite thresholds and invalid preventive/hard ordering are rejected by `RiskConfig`. The OHLC model still cannot observe an unrecorded intrabar mark that does not cause an execution event; this remains an explicit limitation rather than fabricated tick-level behavior.

### Drawdown definition

For every recorded equity point, running peak equity is the cumulative maximum of equity. Drawdown amount is `running_peak_equity - equity`. `drawdown_pct_initial` is the drawdown amount divided by initial capital and is the series used for R-07's 8% initial-capital denominator. `drawdown_pct_peak` is separately exposed as the conventional peak-relative ratio. Drawdown is calculated after forced end-of-data closure updates the final equity row; rejected runs retain the equity and drawdown at the rejection point.

### Equity and P&L accounting

For every recorded point, `cash = initial_capital + realized_pnl`, where `realized_pnl` is the sum of closed trades' net P&L after their actual costs. For an open position, `unrealized_pnl` is the net result at the existing completed-candle liquidation estimate, including entry costs and estimated exit costs; it is zero when flat. `gross_pnl` is midpoint-price P&L before costs, and `total_costs` is actual closed-trade costs plus estimated costs for the open position. The identities are `equity = cash + unrealized_pnl = initial_capital + gross_pnl - total_costs`. On closure, the open contribution becomes zero and its net result enters `realized_pnl` exactly once. `used_margin`, `required_margin`, and `free_margin` continue to derive from the existing position and equity model.

### Event ledger

The returned `BacktestResult.events` tuple contains JSON-serializable dictionaries with deterministic sequence numbers, normalized timestamps, event type, legacy kind, severity, phase, message/explanation, run ID, optional trade/order identifiers, simulated source, compatibility fields, and structured details. The run ID is intentionally run-specific; sequence and simulation content are deterministic for equivalent inputs. Strategy and data validation failures retain the existing raised-exception behavior and expose the same event dictionaries through the exception's `events` attribute.

### Simulated order fills

`ExecutionConfig()` preserves the existing full-fill behavior for entry and exit orders. When `entry_fill_quantity_cap` is set, an entry fills the lesser of the requested quantity and the cap; margin, exposure, costs, position size, and P&L use the filled quantity, and the remainder is deterministically cancelled. No candle volume or inferred liquidity is used. Exit orders remain full-fill in M1; partial-exit accounting is deferred.

### Reproducibility

The backtester canonicalizes the validated timestamp/OHLC columns, strategy definition, and effective cost/margin/risk/data-validation/execution configuration before hashing. Numeric values are normalized, timestamps are converted to UTC, and canonical JSON uses sorted keys and compact separators. Run ID and UTC creation time are generated separately and excluded from `input_hash`, so repeat runs with the same effective inputs keep the same deterministic fingerprint while remaining separate runs. Metadata is JSON-serializable and contains no machine-specific paths or secrets.

### Durable run records and recovery

When `RunPersistenceConfig.directory` is configured, the engine writes one versioned JSON record per run using a temporary file, flush/fsync, and atomic replacement. The checkpoint format is now version 2 because equity rows explicitly persist P&L and cost fields; older version-1 records are rejected as incompatible rather than silently reconstructed. Each record contains a canonical SHA-256 integrity digest over the persisted payload excluding the digest field; this detects unintended changes but is not an authenticity guarantee if an actor can rewrite both payload and digest. Checkpoints are committed after completed-bar equity/risk processing and contain the next bar index, open position, trades, explicit equity components, risk state, margin state, pending entry state, event ledger, fingerprints, and effective configurations. Resume validates the format/version, digest, strategy, validated dataset, bounded progress, saved equity prefix, event sequence/run identifiers, data reference, initial capital, configuration, engine version, and software versions before continuing. A deterministic interruption failpoint is used only by tests; local JSON persistence does not claim recovery from every operating-system or hardware failure. Completed and rejected records are terminal and cannot be resumed.

### Market-data validation

The validator copies input data, normalizes timestamps to UTC, preserves row order, and never fills, sorts, drops, or invents candles. Supported requested timeframes are `1m`, `5m`, `15m`, `30m`, `1h`, `4h`, and `1d`, plus documented `m1`/`m5`/`m15`/`m30`/`h1`/`h4`/`d1` aliases. Reports contain issue code, severity, message, and affected timestamps. Weekend-only gaps are informationally classified as expected closures. Explicitly configured closure dates are also accepted. Other gaps generate `unexpected_gap` and `calendar_unavailable` errors under the conservative policy and cannot enter a backtest. The backtester additionally requires three rows for a next-bar entry, plus configured bar-exit length.

Execution-relevant market data may additionally provide `spread` as a non-negative, finite full bid/ask width in explicit price units, or complete `bid_open`, `bid_high`, `bid_low`, `bid_close`, `ask_open`, `ask_high`, `ask_low`, and `ask_close` columns. Incomplete or inconsistent bid/ask data is rejected. Complete bid/ask data takes precedence over `spread`, and `spread` takes precedence over scalar `CostModel.spread`; unsupported OHLC-only inputs continue to use the scalar fallback. Supported execution fields are normalized on the validation copy and included in the canonical dataset fingerprint, so checkpoint recovery rejects changed spread or quote data.
